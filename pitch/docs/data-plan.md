# 情境與資料應用規劃（yoxi 題第 1 項）

> **回答簡報哪幾頁**：第 2 章「目標對象與痛點」（yoxi 現況、三種使用者、一天裡的空白時刻）＋第 3 章「解決方案設計」的資料頁（資料盤點、「今天的地方」怎麼算、隱私與治理）＋第 6 章「落地評估」的第一步（拿到資料後兩週）。
> **結論三句**：① yoxi 的 app 只在「要出門」那一刻被打開，公開評論裡最常被抱怨的是叫不到車、被取消與優惠券規則，再多發券也換不到「沒事也打開」；② 城事只用三類資料做一個決定：「今天推薦哪一個地方、什麼時候告訴你」——yoxi 的去識別化資料負責冷啟動與時段，使用者自己的足跡負責個人化，公開資料負責內容與天氣；③ 每一筆資料都有退路（關掉它，功能降級但不壞），個人資料分成「只有你／你可分享」兩軌，競賽資料只在競賽環境裡用、賽後銷毀。
> **還沒有答案的事**：yoxi 寄來的資料欄位與粒度（有沒有使用者層級的頻率分布、有沒有供給面的空車資料）；yoxi 目前的 app 開啟頻率與「非叫車開啟」比例（沒有公開數字，全部標「假設」）；背景定位的同意率；+50 點的預算歸屬（見 `business.md`）。

本檔的數字規矩：外部數字附 URL 與查詢日期（2026-09-23）；app 裡的數字照公式（`BRIEF.md` §3）；查不到的寫「假設」並寫怎麼驗。人物全部虛構。

**產品部會從這裡讀到的三件事**：

| # | 讀法 | 對城事的設計約束 |
|---|---|---|
| 1 | 優惠券是 yoxi 現在「讓人打開」的主要工具（「天天領」優惠、新戶 13 張券，見 https://www.yoxi.app/promotion/888 與第三方整理），但評論顯示券的規則本身會變成抱怨來源，而且在叫不到車時完全無效 | 城事不能再是一種券：打開的理由是內容（今天的地方），不是折扣；點數只在搭車抵達時出現，而且有門檻（> 3 km） |
| 2 | 使用者對叫車流程裡的「多出來的東西」非常敏感（廣告、推播關不掉） | 叫車首頁的收合態 0 像素改動、推播一天最多兩則且各自可關、每一類資料可單獨關——這三條是對這些評論的直接回應 |
| 3 | 抱怨最多的是供給（叫不到、被取消），不是需求 | 城事導出的叫車需求要**往運力有餘的時段與方向推**（週末下午、離峰），不是把尖峰更塞；「運力調度」是推薦排序的一個特徵（§4），不是行銷話術 |

### 1.3 叫車 app 的開啟集中在「有需求時」

題目原文已經寫明：「傳統叫車平台的使用場景高度集中在『有明確出行需求時』，這導致 APP 開啟頻率低、用戶黏著度有限。」（`competition.md` §3）我們把它拆成「一週裡哪些時刻完全不會打開」：

| 時刻 | 使用者在做什麼 | 現在會打開 yoxi 嗎 | 為什麼不會 | 城事想接的點 |
|---|---|---|---|---|
| 平日早上通勤（走路或騎車段） | 走到車站、公車站、公司 | 不會（除非下雨、趕時間） | 沒有要叫車 | 早上推播「今天的地方」：一則、離你常走的路 ≤ 3 km |
| 午休 | 吃飯、滑手機 | 不會 | 同上 | 不推播；打開 app 時「今天的地方」已經在那裡 |
| 平日下班後 | 回家、買晚餐 | 偶爾（雨天、加班太晚） | 大多走路或搭大眾運輸 | 回家路上 ≤ 3 km 的地方可以繞一下（不推播，只在打開時） |
| 週末早上決定要去哪 | 查 Google Maps、IG、問家人 | 不會 | yoxi 不提供「去哪」 | 路線與還沒去的地方；走不到的那一站「設為下車點」→ 叫車 |
| 週末出遊回程 | 累了、帶小孩 | 會（這是現有需求） | — | 行程中「這條路上」內容卡；抵達後收下明信片 |
| 晚上滑手機 | 看今天的照片、回 LINE | 不會 | 沒有理由 | 晚上推播「今天的回顧」：四幕、只有你看得到 |
| 長輩的一天 | 早上散步、傳早安圖、看病 | 自己幾乎不會（子女代叫） | 操作門檻、少搭車 | 用他走過的地方排成問候圖，轉傳到家族群組 |

> 開啟次數的量化**全部是假設**：沒有公開資料。§6 H1 用競賽資料的「叫車時段與頻率趨勢」先畫出叫車的時間分布，作為「現在只在這些時刻打開」的下限證據。

## 3. 資料盤點

### 3.1 隱私等級定義

| 等級 | 意思 | 誰看得到 | 存在哪 |
|---|---|---|---|
| **只有你** | 個人、敏感、不分享 | 只有使用者本人 | 優先留在手機；需要跨裝置時加密存帳號下，不進分析 |
| **你可分享** | 使用者主動按分享才會離開手機 | 使用者選的對象 | 帳號下；分享出去的圖不帶座標與時間戳 |

## 4. 「今天的地方」怎麼算

### 4.1 從寫死的五條理由到一個排序邏輯

原型 `prototype/js/mock.js` 的 `TODAY.why` 寫死五條理由（常用地點、常用時段、收集缺口、天氣、活動資料／整修），另外 `FAR_PLACE.why` 有「路線進度、距離判斷、運力調度」。把它們拆成**每條理由對應一個特徵、一筆資料、一個決定**：

| 原型的理由（原文） | 變成哪個特徵 | 用什麼資料 | 它決定什麼 |
|---|---|---|---|
| 常用地點：「你這個月有 9 趟行程從水利路出發，但從沒往北走過那個路口」 | `near_habit`：與使用者錨點的走路距離；`unvisited`：足跡裡沒有 | U1、U3、U4（冷啟動用 Y3） | 候選集的圓心；分數的第一項 |
| 常用時段：「你週日下午通常在家，這是你一週裡最可能出門走走的時段」 | `time_fit`：使用者的空閒時段 × 地點最好的時間 | U2（冷啟動用 Y1）、E6 | 推播時間、這一天推哪個 |
| 收集缺口：「你的圖鑑裡還沒有任何一張『工業遺構』類的明信片」 | `novel_type`：類型新鮮度（不是「差幾張」） | U5 | 小權重加分；**不做**「最快集滿」排序 |
| 天氣：「今天下午 3–6 點降雨機率 10%，西曬角度正好」 | `weather_ok`：過濾＋加分 | E4、E6 | 大雨時戶外不進候選；晴天戶外加分 |
| 活動資料：「此地本週六起封閉整修 90 天」 | `timely`：有活動、有時效的事實 | E2、E3、Y4 | 加分；**文案不寫倒數**（UX 評估建議改成「整修前的樣子，這幾天還看得到」） |
| 運力調度（FAR_PLACE）：「週日下午新竹往內灣方向回程車較多，這個時段叫車較好媒合」 | `supply_ok`：該方向該時段的叫車量低於平常（有空車的代理指標） | Y1、Y3（最好有供給資料，見 §6 待確認） | **只影響 > 3 km 的地方**：什麼時候推「走不到、叫車去」的那一站 |
| 路線進度：「你已收下內灣線的前兩站，這是接下來的一站」 | `route_next`：路線上離你最近、還沒去的一站 | U5、路線內容 | 小權重加分；沒有順序壓力 |

### 4.2 候選集怎麼來

| 步驟 | 規則 | 資料 |
|---|---|---|
| C1 內容池 | 只有**編輯審過、每段事實有出處**的地方才能當候選（AI 草稿不直接上架，見 `ai-architecture.md`） | 內容庫 |

### 4.4 排序特徵與權重（初版，權重是假設，§6 與 pilot 調）

| 特徵 | 值域 | 初始權重（假設） | 資料 | 備註 |
|---|---|---|---|---|
| `near_habit` 離錨點越近越高（常經過卻沒去） | 0–1 | 0.30 | U1、U3、E1 | 冷啟動用 Y3 |
| `time_fit` 你的空閒時段與地點最佳時段重疊 | 0–1 | 0.20 | U2、E6、F2 | 冷啟動用 Y1 城市層級 |
| `timely` 活動／時效 | 0–1 | 0.15 | E2、E3、Y4 | 文案不寫倒數 |
| `weather_ok` 天氣適合度 | 0–1 | 0.10 | E4 | 過濾之後的加分 |
| `novel_type` 類型新鮮度 | 0–1 | 0.10 | U5 | 不是「差幾張」 |
| `route_next` 路線上的下一站 | 0/1 | 0.05 | U5 | 沒有順序壓力 |
| `prior` 群體熱度先驗（休閒類下車熱點附近） | 0–1 | 0.10 | Y2、Y3 | 冷啟動時權重拉到 0.40，隨足跡增加遞減 |
| `supply_ok` 遠處池專用：該時段該方向運力有餘 | 0/1 | 遠處池的門票 | Y1（＋供給資料） | 不成立就不推遠處 |
| `fatigue` 負回饋：同類型連續、剛略過 | 0–1 | −0.20 | U9 | 多樣性 |

**推薦理由的產生**：取分數貢獻最高的 3 條特徵，各自有一個句型（例如 `near_habit` →「你這個月有 {n} 趟行程從 {錨點} 出發，但從沒往 {方向} 走過」）。數字全部從資料算，不手寫；AI 只負責把句子寫順（`ai-architecture.md`）。沒有資料支撐的理由不出現——例如使用者關掉「常用地點」，第一條理由就不會是常用地點。

```text
                        and supply_ok(user.city, direction(anchors, place), slot)):  # C4
            continue
        pool.append((place, d, slot, far))

    if pool is empty: return fallback_station_walk(user)                 # 永遠有一個

    cold = user.footprint_count < 3
    for (place, d, slot, far) in pool:
        f = {
          near_habit: 1 - min(d, WALK_MAX_M) / WALK_MAX_M if not far else 0.2,
          time_fit:   overlap_ratio(slot, free),
          timely:     event_score(place, date),                           # E2/E3/Y4
          weather_ok: weather_fit(place, wx, slot),
          novel_type: 1 if place.type not in user.collected_types else 0.3,
          route_next: 1 if place is next_unvisited_stop(user) else 0,
          prior:      leisure_dropoff_density(place),                     # Y2/Y3
          fatigue:    same_type_recent(user, place.type) + skipped_recent(user, place),
        }
        w = WEIGHTS_COLD if cold else WEIGHTS
        score[place] = dot(w, f)

    today = argmax(score)                                                # F4 一天一個
    reasons = top3_contributions(today, f)                               # 理由文字從這裡來
    push_at = first(free) clamp to allowed_hours(user)                   # F5/F6
    if user.allows_push("am") and pushes_today(user) < 2:
        schedule_push(user, push_at, today, reasons[0])
    log(today, reasons, score, cold)                                     # 供 KPI 與歸因
    return today, reasons
```

|---|---|---|---|---|

### 5.1 競賽資料（去識別化解題資源）的使用邊界

依據：參賽注意事項第 9 條「解題數據僅供本競賽使用，不得外流或用於其他用途，賽後須銷毀」（`competition.md` §3）。

| 項目 | 我們的做法 |
|---|---|
| 存放 | 一個隔離的雲端專案／資料夾，只有隊員帳號可讀；不放進本 repo（`.gitignore` 加上資料目錄，提交前檢查） |
| 使用 | 只做 §6 的分析與簡報圖表；不餵進任何第三方模型的訓練；需要 LLM 摘要時只傳彙總後的表 |
| 產出 | 簡報只放彙總圖（區域 × 時段），不放原始列；格網單位 ≥ 250 m、每格人次 < 10 不顯示（假設門檻，依 yoxi 規範調） |
| 不做 | 嘗試重新識別個人；與其他資料源做個人層級的串接；把衍生出的名單（例如熱門地點排行）寫進 app 的資產檔 |
| 銷毀 | 賽後（2026-11-21 決賽之後）刪除原始資料與所有衍生中間檔，保留一份刪除紀錄（檔名、時間、執行人） |
| 上線後 | 同樣的分析由 yoxi 在自己的系統裡用自己的資料重跑；我們交付的是方法與程式，不是資料 |

### 5.5 法遵會問的其他問題

| 問題 | 回答 |
|---|---|
| 依據什麼法 | 個人資料保護法（https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=I0050021 ）；告知事項寫在首次開啟的說明頁與設定頁 |
| 蒐集目的是否與叫車一致 | 常用地點與時段屬於提供「城市探索推薦」的新目的，所以**單獨告知、單獨同意、可單獨關閉**（設定頁五種資料各自一個開關，原型已有） |
| 推薦是否為自動化決策 | 是，但只決定「推薦哪個地方」，不影響車資、派車與任何權益；推薦理由對使用者可見 |
| AI 生成內容 | 明信片標「AI 生成示意」；地方故事每段有出處；生成時不送任何個人資料，只送地點、季節、時段 |
| 兒少 | 親子情境由家長帳號操作；不蒐集兒童照片到伺服器（照片只在手機端讀） |
| 保存期間 | 只有你的資料：帳號存續期間；彙總資料：依 yoxi 政策；競賽資料：賽後銷毀 |
