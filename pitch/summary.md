# 提案摘要（簡報第 1 頁，不計入 15 頁）

帶「【待填】」的是團隊要決定的；帶「（假設）」的數字要在 `docs/` 找得到算式。

| 欄位 | 內容 |
|---|---|
| 團隊名稱 | 【待填】 |
| 產品/服務名稱 | **yoxi 城事** —— 不搭車也會打開的城市探索與收藏，接回叫車與和泰 Points |
| 企業挑戰題目 | yoxi：不搭車，也打開 yoxi —— 打造高頻互動的AI出行夥伴 |
| 目標對象 | 已經裝了 yoxi、但只有要搭車才打開的都市使用者，以及他們想分享城市給的家人 |
| 解決方案設計重點（至多 3 項） | 1. **一天一個地方**：AI 用叫車時段、常用地點、熱門上下車與活動熱點，每天早上推一個走得到的地方，到了才解鎖明信片與足跡上色；沒搭車也有打開的理由。<br>2. **腳到不了的一段才叫車**：路線與內容頁上「設為下車點」一鍵帶進叫車主流程（3 km 以上才建議搭車），車資與時間當場算；搭車抵達的限定明信片回流和泰 Points。<br>3. **叫車沒有變難用**：第 0 步不動 tab bar 與叫車主畫面；六條防護承諾（DOM 逐節點相同、關鍵路徑 4 tap 不變、收合態 0 像素、叫車地圖最多 4 個景點…）可當場重跑。 |
| 運用到的AI技術、服務或模型等資源 | Google Cloud Vertex AI：Gemini（個人化推薦排序的特徵摘要與理由生成、地方內容草稿、週回顧與日誌敘事）、Imagen（依地點與季節生成明信片與長輩圖）、向量檢索（地方與活動資料）；Cloud Run／Firestore／BigQuery／Pub/Sub；OpenStreetMap 地理資料；yoxi 提供的去識別化叫車時段、POI、熱門上下車與活動熱點資料。 |
| 預期效益簡述 | 目標值（pilot 新竹 12 週，假設，驗證法見簡報第 13 頁）：非叫車日的週開啟率從接近 0 提升到 【待 kpi.md】；探索產生的訂單佔 pilot 用戶訂單 【待 kpi.md】，且叫車關鍵路徑 tap 數維持 4；在地合作從優惠碼升級為內容與落點，合作方分攤限定版點數；每 MAU 每月 AI 與雲端成本 【待 ai-architecture.md】 元（假設），瓶頸在每城一位城市編輯而不是 AI。 |
